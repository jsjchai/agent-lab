# 11 · 模型横向对比

> 对应源文档 §9/§12 · 代码模块 [`m11_model_bench.py`](../m11_model_bench.py) · 运行：`../../.venv/bin/python m11_model_bench.py`

## 一、这是什么 / 为什么重要

[09 模型部署与路由](09-模型部署与路由.md)回答了「怎么按维度选模型」，但有一个前置问题没解决：**每个候选模型到底行不行？**「7B 便宜又快」是印象，「意图准确率 87.5%、平均延迟 1.62s」才是证据。源文档 §9 的路由维度里「质量要求：任务所需能力和评测结果」与「延迟：响应时间」，都要靠实测数据填充；§12 的门槛也强调「需 POC 实测校准」。模型横向对比基准（benchmark）就是生产这些数据的装置。

对 Teaching 的具体意义：活动创建是**交互式**流程，意图抽取每多一秒用户就多等一秒；而槽位抽错一个字段，后面澄清、草稿、校验全跟着错。所以选型不是「挑最大的模型」，而是在**准确率、格式稳定性、延迟**三者之间为每类任务找平衡点。

[`m11_model_bench.py`](../m11_model_bench.py) 对同一组任务（8 条意图抽取 + 5 条 RAG 问答）跑多个模型（mock 基线 / qwen2.5:7b / qwen3:8b），量化五个指标：意图准确率、**槽位漂移次数**、JSON 校验重试次数、平均延迟、RAG 引用/拒答准确率。结果写入 `out/model_bench.json`，供 webui「评测与安全」面板展示。README 给出的实测结论（M2 Max，Ollama）：

| 模型 | 意图准确率 | 槽位漂移 | JSON重试 | 意图延迟 | RAG引用 | RAG拒答 |
|---|---|---|---|---|---|---|
| mock（基线） | 100% | 0/8 | 0 | 0s | 100% | 100% |
| qwen2.5:7b | 87.5% | 3/8 | 0 | 1.62s | 100% | 100% |
| qwen3:8b | 100% | 2/8 | 0 | 13.67s | 100% | 100% |

这张表直接支撑了路由决策：**延迟敏感的意图抽取用 7B + 归一化兜底；质量敏感且可接受延迟的任务用 8B**——这正是 m09 路由器按「任务类型/质量/延迟」分流的依据。

## 二、核心概念详解

### 2.1 基准设计：控制变量 + 基线 + 端到端口径

**定义**：基准测试 = 固定任务集 + 固定评测口径 + 多个被测对象，输出可横向比较的量化指标。

**为什么**：模型对比最怕「各测各的」——Prompt 不同、后处理不同、用例不同，结论就没有可比性。必须控制变量：所有模型走**同一条生产链路**（同样的 Prompt、同样的校验重试、同样的归一化、同样的 RAG 检索与引用校验），只换模型本身。

**本项目体现**：
- 任务集硬编码在模块里：`INTENT_CASES`（8 条）与 `RAG_CASES`（5 条），每条带 ground truth；
- 意图链路复用 [`m02_intent_slots.py`](../m02_intent_slots.py) 的 `build_messages` / `_validate_intent` / `_normalize`——与线上工作流**完全同一套代码**，测的就是生产行为；
- RAG 链路复用 [`m06_rag.py`](../m06_rag.py) 的 `KnowledgeIndex`，每个模型**重建索引**（向量模型不同，见坑 4）；
- **mock 是基线而非选手**：它是确定性规则替身，100%/零漂移代表「链路与断言的上界参照」，用来确认基准本身没写错，不代表任何模型能力。

### 2.2 准确率：子集匹配 + 缺项严格相等

**定义**：意图抽取准确率 = 归一化后的输出符合 ground truth 的用例占比。

**为什么这样判**：槽位用**子集匹配**（只检查期望的键值，模型多抽了 grade 等额外信息不算错——信息多是好事）；缺项用**集合严格相等**（多报缺项会多问用户、漏报缺项会建错活动，两个方向都算错）。这比 m08 的缺项断言（`issubset`，容忍多报）更严，因为选型基准要区分模型的边界判断能力，不能放水。

**本项目体现**（`bench_intent` 内）：

```python
slots_ok = all(norm["slots"].get(k) == v for k, v in want_slots.items())
missing_ok = set(norm["missingFields"]) == set(want_missing)
ok = slots_ok and missing_ok
```

知识问答类用例（`want_missing is None`）只查 `intent == "knowledge_qa"`——问答题不需要槽位。

### 2.3 槽位漂移：小模型格式稳定性的直观指标

**定义**：模型**原始输出**与**归一化后输出**不一致的用例数。README 的原话：「『槽位漂移』= 原始模型输出需经 `_normalize` 纠正的用例数，是衡量小模型格式稳定性的直观指标。」

**为什么重要**：准确率只告诉你「兜底之后对不对」，漂移告诉你「兜底之前有多不稳」。一个准确率 100% 但漂移 8/8 的模型，意味着整条链路完全依赖代码纠偏——兜底逻辑一旦有洞就全线崩溃。漂移是**风险指标**，准确率是**结果指标**，两者必须一起看。

**本项目体现**：判定逻辑（`bench_intent` 内）——JSON 校验重试后仍失败（`"_error" in raw`）回退规则抽取，计一次漂移；否则比较原始与归一化结果：

```python
norm = m02._normalize(raw, text)
if raw.get("slots") != norm["slots"] or set(raw.get("missingFields", [])) != set(norm["missingFields"]):
    drift += 1
```

实测解读：7B 漂移 3/8（README 记录的典型漂移：`speakers:""`、`speaker_count:"两位"`、missingFields 用中文键名、「下周」被当具体日期）；**8B 也有 2/8**——所以「即便 8B 也需归一化纠正，格式兜底不能省」。注意漂移 ≠ 错误：8B 漂移 2 例但准确率 100%，说明归一化把漂移全部救回来了。

### 2.4 JSON 校验重试：结构化输出的最后一道闸

**定义**：`chat_json` 对模型输出做结构校验，不合格就把失败原因追加进对话让模型重输出，最多重试 2 次（共 3 次尝试）；仍失败返回 `{"_error": ...}`。重试次数从 `LLM.stats["errors"]` 的增量统计。

**为什么**：小模型偶发输出围栏包裹、多余说明、漏字段（§3「未经校验的模型输出不能进入业务流程」）。校验重试把「偶发格式错误」消化在调用层，而不是让它污染下游。

**本项目体现**：`llm.chat_json(m02.build_messages(text), validate=m02._validate_intent, retries=2)`；每个用例前后快照 `llm.stats["errors"]` 求差得到该用例的重试消耗。实测两个真实模型都是 **0 次重试**——说明它们的 JSON 大体规范，问题主要在语义/类型层（漂移），而非解析层。这本身就是一个有价值的结论：重试机制是保险丝，平时不烧。

### 2.5 延迟与准确率-延迟权衡

**定义**：延迟 = 单用例从发起到拿到可用输出的墙钟时间，取平均。意图延迟计整个 `chat_json`（含重试）；RAG 延迟计整个 `index.answer`（含 embedding、检索、生成）。

**为什么权衡**：交互式场景延迟直接是用户体验；后台批处理则可以拿时间换质量。没有「最好的模型」，只有「该任务最合适的模型」。

**本项目体现**：实测 8B 意图准确率 100% 但延迟 **13.67s**，7B 87.5% 但 **1.62s**——8 倍延迟差的主要原因是 **qwen3 默认带思考过程**（README 原话）。于是选型建议自然导出：意图抽取（高频、交互、有归一化兜底）用 7B；质量敏感且可接受延迟的任务用 8B。RAG 两个模型引用/拒答都 100%，说明「检索 + 引用校验」链路对两者都稳健，RAG 的模型选择可以更多考虑延迟与成本。

## 三、代码实现解析

### 3.1 make_llm：统一构造被测模型

来源：[`m11_model_bench.py`](../m11_model_bench.py)

```python
OLLAMA_BASE = "http://localhost:11434/v1"

def make_llm(model: str) -> LLM:
    if model == "mock":
        return LLM("mock")
    return LLM("openai", model=model, base_url=OLLAMA_BASE, api_key="ollama", embed_model="bge-m3")
```

设计意图：所有真实模型统一走本地 Ollama 的 OpenAI 兼容端点（`api_key="ollama"` 是占位，Ollama 不校验），RAG 向量统一用 bge-m3——**向量模型也是控制变量**，否则 RAG 差异分不清是生成模型还是 embedding 造成的。`LLM` 实例级参数覆盖（见 [`common/llm.py`](../common/llm.py)）让同一进程内并存多个模型客户端，互不串配置。

### 3.2 INTENT_CASES 与 RAG_CASES：带 ground truth 的任务集

来源：[`m11_model_bench.py`](../m11_model_bench.py)

```python
# (输入, 期望槽位子集, 期望缺项；None 表示问答题只查 intent)
INTENT_CASES = [
    ("创建11月20日的数学教研活动，面向三年级教师，主讲人：张三、李四",

    ...
    ("什么是教研活动？", {}, None),
    ("创建数学教研活动，11月20日，面向三年级教师", {"subject": "数学", "date_text": "11月20日"}, ["speakers"]),
]

# (问题, 用户, 是否可答)
RAG_CASES = [
    ("活动时长有什么规定？", "u1", True),
    ("如何查询轮转计划？", "u1", True),
    ("文档入库的流程是什么？", "u3", True),
```

设计意图：8 条意图用例覆盖完整创建、模糊时间（「下周」→ 缺 date_text）、数量短语（「两位主讲人」→ 缺 speakers）、极简输入（缺 4 项）、年级槽位、问答分流、单缺项——正是 §4 要求的真实表达形态。RAG 5 条里 3 可答 2 不可答，且「文档入库」特意用 **u3（t2 租户）**，顺带验证 ACL 正向可达；两条不可答问题（量子力学/食堂）是典型的「语义无关但向量相似度不为零」陷阱，考验拒答链路。

### 3.3 bench_intent：一次循环量化四个指标

来源：[`m11_model_bench.py`](../m11_model_bench.py)

```python
def bench_intent(llm: LLM) -> dict:
    correct, drift, retries, latencies = 0, 0, 0, []
    for text, want_slots, want_missing in INTENT_CASES:
        err_before = llm.stats["errors"]
        t0 = time.time()
        raw = llm.chat_json(m02.build_messages(text), validate=m02._validate_intent, retries=2)
        if "_error" in raw:
            norm = mock_extract_intent(text)
            drift += 1
        else:
            norm = m02._normalize(raw, text)
            if raw.get("slots") != norm["slots"] or set(raw.get("missingFields", [])) != set(norm["missingFields"]):
                drift += 1
        latencies.append(time.time() - t0)
        retries += llm.stats["errors"] - err_before

        if want_missing is None:
            ok = norm.get("intent") == "knowledge_qa"
        else:
            slots_ok = all(norm["slots"].get(k) == v for k, v in want_slots.items())
            missing_ok = set(norm["missingFields"]) == set(want_missing)
            ok = slots_ok and missing_ok
        correct += ok
    n = len(INTENT_CASES)
    return {
        "accuracy": round(correct / n, 3),
        "drift_cases": drift,
        "json_retries": retries,
        "avg_latency_s": round(sum(latencies) / n, 2),
        "cases": n,
    }
```

设计意图逐点讲：

1. **与生产同链路**：直接调 m02 的 `build_messages`/`_validate_intent`/`_normalize`，不另写一套「评测专用 Prompt」——评的就是线上行为，结论可直接指导路由。
2. **失败兜底也计漂移**：`_error` 时回退 `mock_extract_intent`（与 `m02.recognize` 的兜底一致），保证基准流程不崩，同时把这次「模型彻底失败」记为漂移——兜底救场不能抹掉模型的失败记录。
3. **漂移检测用原始 vs 归一化对比**：而不是「归一化后 vs ground truth」。前者测格式稳定性（模型问题），后者测准确率（链路结果），两个维度解耦。
4. **重试用 stats 增量**：`err_before` 快照求差，无需侵入 `chat_json` 内部；`LLM.stats["errors"]` 在每次校验失败时 +1（见 common/llm.py），天然就是重试计数器。
5. **延迟包含重试**：计时包住整个 `chat_json`，重试的代价如实反映——「格式不稳」最终会换算成延迟。

### 3.4 bench_rag：每模型重建索引 + 引用/拒答断言

来源：[`m11_model_bench.py`](../m11_model_bench.py)

```python
def bench_rag(llm: LLM) -> dict:
    index = m06.KnowledgeIndex(llm)
    index.build()
    cite_ok, answerable, refuse_ok, refusals, latencies = 0, 0, 0, 0, []
    for query, user, answerable_q in RAG_CASES:
        ctx = authenticate(user)
        t0 = time.time()
        ans = index.answer(ctx, query)
        latencies.append(time.time() - t0)
        if answerable_q:
            answerable += 1
            cite_ok += bool(ans.get("citations")) and set(ans["citations"]).issubset(set(ans.get("retrieved", [])))
        else:
            refusals += 1
            refuse_ok += (not ans.get("citations"))
    return {
        "citation_accuracy": round(cite_ok / max(answerable, 1), 3),
        "refusal_accuracy": round(refuse_ok / max(refusals, 1), 3),
        "avg_latency_s": round(sum(latencies) / len(RAG_CASES), 2),
    }
```

设计意图：
- **每个模型新建 KnowledgeIndex 并 build**：mock 用 256 维哈希向量、真实模型用 bge-m3，维度与语义空间完全不同，§8 规则「不同 Embedding 模型或维度的向量不能直接混用」在这里是硬约束。m06 内部还会按维度切换相关性门槛（`vec_thr = 0.25 if self.dim <= 256 else 0.5`），因为 bge-m3 对无关文档也有 ~0.3–0.4 相似度。
- **引用断言与 m08 同口径**：非空且 ⊆ 实际检索片段，编造引用必被抓。
- **拒答断言略宽于 m08**：这里只查 `not citations`（m08 还要求文本含「无法确认」）——基准关注「有没有硬答」，措辞检查留给门禁。
- `max(answerable, 1)` 防除零；身份经 `authenticate` 走可信链路，评测不伪造身份。

### 3.5 run 与 main：容错执行 + 产物落盘

来源：[`m11_model_bench.py`](../m11_model_bench.py)

```python
def run(models: list[str]) -> dict:
    rows = []
    for model in models:
        print(f"  ⏳ {model} ...", flush=True)
        llm = make_llm(model)
        try:
            intent = bench_intent(llm)
            rag = bench_rag(llm)
            rows.append({"model": model, "intent": intent, "rag": rag, "error": None})
            ...
        except Exception as exc:
            rows.append({"model": model, "intent": None, "rag": None, "error": str(exc)[:120]})
            print(f"     ✗ 失败：{exc}")
    return {"generated_at": time.strftime("%Y-%m-%d %H:%M:%S"), "models": rows}
```

设计意图：**单模型失败不拖垮整场基准**——Ollama 没起、某个模型没 pull，只会在该行留下 `error` 字段，其余模型照常出数。这对「多模型对比」尤其重要：环境缺一个模型是常态。`generated_at` 时间戳让结果可追溯（模型/硬件/日期都是结论的前提）。`main()` 用 argparse 提供 `--models`（默认 `["mock", "qwen2.5:7b", "qwen3:8b"]`）与 `--out`（默认 `out/model_bench.json`），JSON 产物被 webui「评测与安全」面板读取渲染成对比表。

### 3.6 selftest：只跑 mock 基线

来源：[`m11_model_bench.py`](../m11_model_bench.py)

```python
def selftest() -> None:
    """mock 基线快速自检（真实模型对比请用 CLI 运行，耗时较长）。"""
    llm = make_llm("mock")
    intent = bench_intent(llm)
    rag = bench_rag(llm)

```

设计意图：`run_all.py` 总验收要求秒级、离线、确定性，所以 selftest 只验证「基准装置本身正确」——mock 基线必须 100% 零漂移，否则说明任务集/断言/链路有 bug。真实模型对比是分钟级操作（8B 单意图用例就 ~14s），走 CLI 手动触发，不进 CI。

## 四、工程要点与常见坑

1. **把 mock 的 100% 当模型能力**
   现象：报告写「本系统意图准确率 100%」。原因：mock 是规则替身，100% 只证明基准装置正确。对策：mock 仅作基线；能力结论必须来自真实模型行（7B 87.5% / 8B 100%），且注明硬件与日期（M2 Max、Ollama）。

2. **只看准确率不看漂移**
   现象：选了「准确率达标」的模型，上线后下游频繁拿到脏结构。原因：准确率是归一化兜底**之后**的结果，掩盖了原始输出的不稳定。对策：漂移与准确率并读——7B 3/8、8B 2/8 说明任何模型都不能省掉 `_normalize`；漂移高的模型要重点加固兜底并监控回退率。

3. **忽视 8B 的思考模式延迟**
   现象：把 8B 配到交互式意图抽取，用户每句话等 13.67s。原因：qwen3 默认带思考过程，延迟是 7B 的 8 倍多。对策：按 README 选型建议分流——交互意图用 7B + 兜底，质量敏感任务才用 8B；若尝试关闭思考模式，必须重跑基准确认准确率没有回落。

4. **跨模型混用向量索引**
   现象：换模型后 RAG 检索质量诡异下降。原因：mock 256 维哈希向量与 bge-m3 语义向量空间不同，混用等于拿英氏尺子量厘米。对策：`bench_rag` 每模型重建索引；生产遵守 §8「模型切换建立新索引版本，回填完成再切 Alias」。

5. **小样本延迟当 SLA**
   现象：拿 8 条用例的平均延迟承诺 P95。原因：样本小、无预热（首次加载模型慢）、无并发压测。对策：平均延迟只用于横向比较；生产扩样本、记录 P50/P95（§12 性能维度）、预热后再测，并固定硬件环境。

6. **一个模型不可用整场基准崩溃**
   现象：没 pull qwen3:8b，结果连 mock/7B 的数据都没了。原因：异常未隔离。对策：`run()` 逐模型 try/except，失败行留 `error` 字段；先 `ollama pull` 对应模型与 bge-m3 再跑。

7. **拿原始输出直接对 ground truth**
   现象：明明线上工作流正常，基准却判模型「准确率很低」。原因：口径错位——线上消费的是归一化后的结构。对策：准确率评归一化后输出（端到端口径），漂移单独评原始输出（模型口径），两个指标各司其职，不混用。

## 五、验收与测试

**selftest 断言**（见 3.6）：mock 基线 `accuracy == 1.0`、`drift_cases == 0`、`citation_accuracy == 1.0`、`refusal_accuracy == 1.0`。四条断言守住「基准装置正确」：任务集可被确定性替身全对、漂移检测不误报、RAG 断言口径与 m06/m08 一致。它被 [`run_all.py`](../run_all.py) 以「m11_model_bench · §9/§12 模型横向对比（mock 基线）」纳入 11 模块总验收。

**对应源文档验收**：
- §9「至少接入两种模型配置；统计调用量、成本、延迟和失败率」——本模块默认三模型配置，延迟/重试/失败（error 行）均有量化；成本维度可接 `LLM.stats` token 数扩展（练习 4）。
- §9「质量要求：任务所需能力和评测结果」——准确率/漂移就是路由的质量输入。
- §12「初始门槛需 POC 实测校准」——7B 87.5% 低于 m08 意图门槛 90%，正是「门槛会真的拦人」的实证；校准动作（改 Prompt/加兜底/换路由）由这里的数据驱动。

## 六、与其他模块的关系

- **[02 Prompt 与上下文工程](02-Prompt与上下文工程.md)（m02）**：基准复用其 `build_messages`/`_validate_intent`/`_normalize` 全套——漂移指标测的正是「模型原始输出 vs m02 归一化」的差距；m02 的兜底设计（缺项代码重算、最后日期覆盖）在漂移数据里得到价值验证。
- **[06 RAG 与知识问答](06-RAG与知识问答.md)（m06）**：RAG 基准复用 `KnowledgeIndex` 完整链路（ACL/混合检索/引用校验/拒答）；两模型引用/拒答均 100% 证明该链路对模型差异稳健。
- **[09 模型部署与路由](09-模型部署与路由.md)（m09）**：本模块是路由的**数据供给方**——质量/延迟维度靠这里实测填充；README 的选型建议（7B 交互意图、8B 质量敏感）就是 m09 配置的依据。
- **[08 评测与质量门禁](08-评测与质量门禁.md)（m08）**：分工明确——m08 是「当前配置过不过门槛」的**门禁**（固定 Golden Set、达标/不达标），m11 是「候选模型谁更合适」的**选型基准**（多模型横向、连续指标）；两者都是确定性断言，m11 数据反过来校准 m08 门槛。
- **[03 模型接入与流式接口](03-模型接入与流式接口.md) / [`common/llm.py`](../common/llm.py)**：`chat_json` 校验重试与 `stats["errors"]` 计数是重试指标的来源；实例级模型参数覆盖让多模型并存成为可能。
- **webui**：`out/model_bench.json` 是「评测与安全」面板模型对比表的数据源。

## 七、动手练习与延伸

1. **扩充任务集**：把 `INTENT_CASES` 扩到 20+ 条（从 m02 的 21 条回归集与 golden_set 移植，补上 grade/speaker_count 等期望），观察小样本结论是否稳定；思考为什么 §12 要求 Golden Set ≥100。
2. **漂移细分**：在 drift 判定处记录「哪个键漂移了」（speakers 类型？missingFields 命名？date_text 旧值？），输出漂移分布——定位兜底逻辑最该加固的位置。
3. **接入云端模型对比**：扩展 `make_llm`，支持 `--models deepseek-chat` 等云端模型（读环境变量 Key/Base URL，注意数据合规：含敏感信息的用例只能跑 PRIVATE_ONLY 模型，见 m09）；把云/私延迟与质量放进同一张表。
4. **补成本维度**：用 `llm.stats["prompt_tokens"/"completion_tokens"]` × 单价估算每模型单任务成本，对照 §12「单任务 Token/费用」与 §9 成本预算维度，输出「准确率-延迟-成本」三维权衡表。
5. **Prompt A/B**：固定模型，换 m02 的 `PROMPT_VERSION`（如改 few-shot 示例）重跑基准，量化 Prompt 变更对准确率/漂移的影响——这就是 §4「Prompt 变更触发回归测试」的量化形态。
