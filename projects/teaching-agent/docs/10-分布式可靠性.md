# 10 · 分布式可靠性

> 对应源文档 §10 · 代码模块 [`m10_reliability.py`](../m10_reliability.py) · 运行：`../../.venv/bin/python m10_reliability.py`

## 一、这是什么 / 为什么重要

教学活动 Agent 里有大量**长任务**：一次活动创建要经过意图抽取、澄清等待、工具查询、草稿校验、用户确认、调用业务 API，中间任何一步都可能遇到模型超时、服务重启、MQ 重复投递。§6 设计原则第 4 条说得很硬：「长任务状态必须持久化，不能只依赖 JVM 内存。」§10 进一步给出异步任务可靠性的完整机制清单：Outbox、幂等键、租约和心跳、指数退避、死信队列、补偿、取消，以及任务状态机。

这些机制各自回答一个故障问题：

- 数据库改了、消息没发出去（或反过来）怎么办？→ **Outbox**
- MQ 把同一条消息投了两次，业务会不会做两遍？→ **幂等键**
- Worker 领了任务就宕机，任务会不会永远卡死？→ **租约 + 心跳**
- 模型超时后立刻重试，会不会把下游打得更死？→ **指数退避**
- 一直失败的任务去哪儿？→ **死信 / 转人工**
- 用户中途反悔，哪些状态能安全取消？→ **取消边界**

§10 的验收标准只有三句话，但每句都对应一类生产事故：「重复消息不产生重复业务操作；Worker 宕机后任务可恢复；失败任务可追踪、重试或转人工。」对 Teaching 而言，「重复业务操作」就是同一个教研活动被创建两次、「任务卡死」就是用户确认后活动永远建不出来——都是必须为零的事故。

[`m10_reliability.py`](../m10_reliability.py) 用 **SQLite 完整模拟 RocketMQ + MySQL** 的这套机制（README 对照表：「RocketMQ + MySQL Outbox → SQLite tasks + outbox 同事务」），单文件可离线演练全部故障场景。机制本身与存储无关，生产把 SQLite 换成 MySQL、把模拟投递换成 RocketMQ，逻辑一一对应。

## 二、核心概念详解

### 2.1 Outbox：数据库提交与消息发送的一致性

**定义**：把「业务状态变更」和「待发消息」写进**同一个本地事务**，再由独立的投递者把 outbox 表里的消息发往 MQ。

**为什么**：「改库」和「发 MQ」是两个系统的操作，无法用一个事务包住。先改库后发消息——中间宕机，任务状态变了但永远没人执行；先发消息后改库——中间宕机，消息到了但任务不存在。Outbox 把跨系统一致性问题降级为「本地事务 + 至少一次投递」：消息可能重发（靠幂等兜底），但不会丢。

**本项目体现**：`tasks` 与 `outbox` 两张表，`enqueue` 在同一事务写两张表；`dispatch` 轮询 `published=0` 的行模拟投递。详见 3.2。

### 2.2 幂等键：重复投递不产生重复业务操作

**定义**：给每个任务的**业务效果**绑定一个唯一键（idem_key），用唯一约束保证同一键的效果只落库一次。

**为什么**：MQ 的投递语义是 at-least-once（至少一次），重复投递是常态而非异常；租约回收重跑也会让同一任务被执行多次。不能指望「消息只来一次」，必须让「执行多次 = 执行一次」。

**本项目体现**：`effects` 表以 `idem_key TEXT PRIMARY KEY`，执行成功时 `INSERT OR IGNORE`——第二次插入被唯一约束静默忽略，`rowcount==0`，业务写入计数不增。这与 [`common/business.py`](../common/business.py) 的 `create_activity_api(ctx, draft, idempotency_key)` 形成**双层幂等**：任务层去重 + 业务 API 自身的 `_IDEMPOTENCY` 去重，任何一层被绕过另一层仍然兜底。对应 §12 门禁指标「重复业务写入 = 0」。

### 2.3 租约与心跳：识别异常退出的 Worker

**定义**：Worker 领取任务时获得一个有期限的「租约」（lease_until）；执行期间定期心跳续租；租约过期仍未完成，说明 Worker 大概率已死，任务被回收重派。

**为什么**：Worker 宕机不会通知任何人，任务会永远停在 RUNNING。没有租约，只能靠人工巡检发现卡死任务。租约把「Worker 活着」变成一个可自动验证的命题：到期没续租 = 死了。

**本项目体现**：`LEASE_SECONDS = 0.2`（演示值，生产要大于任务 P99 耗时并靠心跳续租）；`claim` 写 `lease_until = now + LEASE_SECONDS`；`heartbeat` 续租且校验 worker 身份；`reap_expired` 把过期 RUNNING 批量重置为 QUEUED。详见 3.4。

### 2.4 指数退避：控制重试节奏

**定义**：重试间隔按指数增长（base × 2^(n-1)），而不是固定间隔或立即重试。

**为什么**：模型超时往往意味着下游过载，立即重试等于火上浇油（重试风暴）。指数退避给下游恢复时间，同时用最大重试次数封顶，避免无限重试。

**本项目体现**：`BACKOFF_BASE = 0.05`，第 1 次失败等 0.05s、第 2 次等 0.1s；`MAX_ATTEMPTS = 3` 封顶。重试时间写进 `next_retry_at`，`claim` 只领取到点的 RETRY_WAIT 任务——退避不是 Worker 原地 sleep，而是**任务级别的调度约束**，Worker 可以去干别的活。

### 2.5 死信与转人工

**定义**：超过最大重试仍失败的任务进入死信队列（DLQ），停止自动重试，交由人工处理。

**为什么**：有些故障不会自愈（模型服务下线、数据本身有问题）。无限重试浪费资源且掩盖问题；直接丢弃则任务无声消失。死信让失败**可见、可追踪、可介入**。

**本项目体现**：`TransientError` 重试耗尽（attempts ≥ 3）→ 状态 `NEEDS_HUMAN`；`PermanentError`（不可重试错误，如参数非法）→ 直接 `FAILED`，一次都不重试。区分两类错误是关键：对可重试错误才退避，对不可重试错误重试毫无意义。`NEEDS_HUMAN` 衔接 §6 的 HITL 与 §10 状态机，运营可在看板上看到并介入。

### 2.6 补偿：处理部分成功

**定义**：多步操作中某步失败后，用反向操作撤销已完成步骤（或向前补完），使整体回到一致状态，典型如 Saga 模式。

**为什么**：分布式下没有跨服务大事务，「第一步成功第二步失败」是常态，必须显式定义如何收场。

**本项目体现（诚实边界）**：m10 **没有实现显式补偿逻辑**，模块聚焦 Outbox/幂等/租约/退避/死信/取消。这与 Teaching 的架构选择有关：§11 规定 Agent 不直接写业务表，最终创建由原业务 API 在**自己的事务**里完成，Agent 侧只有只读查询与草稿构建——部分成功的暴露面被架构压缩了。生产中若出现跨服务多步写（例如创建活动 + 通知 + 排期），仍需按 §10 补补偿逻辑，见练习 4。

### 2.7 取消：定义可取消边界

**定义**：明确哪些状态的任务可以安全取消，哪些不能。

**为什么**：RUNNING 的任务可能已经产生副作用（消息已发、业务已写），此时「取消」无法简单回滚，强行取消会留下半完成状态。取消必须是**状态机上的合法迁移**，而不是任意时刻的开关。

**本项目体现**：`cancel` 只接受 `PENDING / QUEUED / RETRY_WAIT`（尚未产生业务效果）→ `CANCELLED`；`RUNNING` 及终态一律返回 False。demo 第 5 幕专门演示这条边界。

### 2.8 任务状态机

§10 建议的状态机在本模块完整落地（模块 docstring 原样给出）：

```text
PENDING -> QUEUED -> RUNNING -> SUCCEEDED / RETRY_WAIT / FAILED / NEEDS_HUMAN / CANCELLED
```

各迁移的代码位置：

| 迁移 | 触发 | 代码 |
|---|---|---|
| PENDING → QUEUED | outbox 投递 | `dispatch`（带 `WHERE status='PENDING'` 守卫） |
| QUEUED → RUNNING | Worker 领取 | `claim` |
| RETRY_WAIT → RUNNING | 退避到点再领取 | `claim`（`next_retry_at<=now`） |
| RUNNING → RUNNING（换主） | 租约过期回收 | `reap_expired` → QUEUED，或 `claim` 直接领过期 RUNNING |
| RUNNING → SUCCEEDED | 执行成功 + 幂等落库 | `execute` |
| RUNNING → RETRY_WAIT | TransientError 且未耗尽 | `execute` |
| RUNNING → NEEDS_HUMAN | TransientError 耗尽 3 次 | `execute` |
| RUNNING → FAILED | PermanentError | `execute` |
| PENDING/QUEUED/RETRY_WAIT → CANCELLED | 用户取消 | `cancel` |

## 三、代码实现解析

### 3.1 常量、错误类型与表结构

来源：[`m10_reliability.py`](../m10_reliability.py)

```python
MAX_ATTEMPTS = 3
BACKOFF_BASE = 0.05
LEASE_SECONDS = 0.2

class TransientError(Exception):
    """可重试错误（如模型超时）。"""

class PermanentError(Exception):
    """不可重试错误。"""
```

```python
def _init(self):
    self.conn.executescript("""
    CREATE TABLE IF NOT EXISTS tasks(
        id TEXT PRIMARY KEY, status TEXT, payload TEXT, idem_key TEXT,
        attempts INTEGER DEFAULT 0, next_retry_at REAL DEFAULT 0,
        lease_until REAL DEFAULT 0, worker TEXT);
    CREATE TABLE IF NOT EXISTS outbox(
        id INTEGER PRIMARY KEY AUTOINCREMENT, task_id TEXT, published INTEGER DEFAULT 0);
    CREATE TABLE IF NOT EXISTS effects(
        idem_key TEXT PRIMARY KEY, result TEXT);
    """)
    self.conn.commit()
```

设计意图：三张表各司其职——`tasks` 是状态机载体（status/attempts/next_retry_at/lease_until/worker 五个字段分别支撑状态、重试计数、退避、租约）；`outbox` 是待发消息队列（published 标志）；`effects` 是业务效果去重表（**主键就是幂等键**，去重由数据库约束保证而非应用代码判断）。`TaskEngine.__init__` 默认 `:memory:` 内存库便于测试，`business_writes` 计数器专门用来断言「真实业务写入只发生一次」。错误类型二分（Transient/Permanent）让重试策略在异常类型上就分流，不需要解析错误字符串。

### 3.2 enqueue 与 dispatch：Outbox 同事务

来源：[`m10_reliability.py`](../m10_reliability.py)

```python
# -- Outbox：同一事务写任务 + 待发消息
def enqueue(self, task_id: str, payload: str, idem_key: str):
    with self.conn:
        self.conn.execute("INSERT INTO tasks(id,status,payload,idem_key) VALUES(?,?,?,?)",
                          (task_id, "PENDING", payload, idem_key))
        self.conn.execute("INSERT INTO outbox(task_id) VALUES(?)", (task_id,))

# -- 投递（模拟 MQ，可能重复）
def dispatch(self):
    rows = self.conn.execute("SELECT id, task_id FROM outbox WHERE published=0").fetchall()
    for r in rows:
        with self.conn:
            self.conn.execute("UPDATE tasks SET status='QUEUED' WHERE id=? AND status='PENDING'", (r["task_id"],))
            self.conn.execute("UPDATE outbox SET published=1 WHERE id=?", (r["id"],))
    return len(rows)
```

设计意图：`with self.conn:` 是 SQLite 的事务上下文（正常退出提交、异常回滚），两条 INSERT **要么都成功要么都不成功**——不存在「任务建了但消息没记」的中间态。dispatch 里状态更新与 published 标记也在同一事务，投递者宕机重启后重新扫 `published=0` 即可，最多重投不会丢。注意 UPDATE 带 `AND status='PENDING'` 守卫：重复投递一条已 RUNNING/SUCCEEDED/CANCELLED 的任务消息时，状态不会被拉回 QUEUED——**消息可以重复，状态机不回退**。

### 3.3 redeliver：主动制造重复投递

来源：[`m10_reliability.py`](../m10_reliability.py)

```python
def redeliver(self, task_id: str):
    """模拟 MQ 重复投递同一条消息。"""
    with self.conn:
        self.conn.execute("INSERT INTO outbox(task_id,published) VALUES(?,0)", (task_id,))
    self.dispatch()
```

设计意图：故障不是等来的，是演练出来的。redeliver 再插一条未发布消息并投递，精确复现 RocketMQ 的重复投递场景，供 selftest 断言 `business_writes == 1`。

### 3.4 claim / heartbeat / reap_expired：租约三件套

来源：[`m10_reliability.py`](../m10_reliability.py)

```python
def claim(self, worker: str):
    now = time.time()
    row = self.conn.execute(
        "SELECT * FROM tasks WHERE (status='QUEUED') "
        "OR (status='RETRY_WAIT' AND next_retry_at<=?) "
        "OR (status='RUNNING' AND lease_until<?) LIMIT 1",
        (now, now),
    ).fetchone()
    if row is None:
        return None
    with self.conn:
        self.conn.execute("UPDATE tasks SET status='RUNNING', worker=?, lease_until=? WHERE id=?",
                          (worker, now + LEASE_SECONDS, row["id"]))
    return dict(self.conn.execute("SELECT * FROM tasks WHERE id=?", (row["id"],)).fetchone())

def heartbeat(self, task_id: str, worker: str):
    with self.conn:
        self.conn.execute("UPDATE tasks SET lease_until=? WHERE id=? AND worker=?",
                          (time.time() + LEASE_SECONDS, task_id, worker))

def reap_expired(self):
    with self.conn:
        cur = self.conn.execute("UPDATE tasks SET status='QUEUED', worker=NULL WHERE status='RUNNING' AND lease_until<?",
                                (time.time(),))
    return cur.rowcount
```

设计意图：
- `claim` 一条 SQL 覆盖三种可领取情形：新任务（QUEUED）、退避到点（RETRY_WAIT 且 next_retry_at ≤ now）、**租约过期的 RUNNING**（宕机 Worker 留下的孤儿）。第三种让回收不依赖定时任务也能发生。
- 领取即写 `worker` 与 `lease_until`，租约从领取那一刻生效。
- `heartbeat` 的 `WHERE id=? AND worker=?` 是身份守卫：旧 Worker 复活后不能给已被别人领走的任务续租。
- `reap_expired` 是显式批量回收（返回回收数量，可作监控指标），把过期 RUNNING 重置为 QUEUED 并清空 worker，等待新 Worker 领取。demo 第 2 幕：`claim("dead-worker")` 后不心跳、sleep 超过租约、reap、换 w2 领取执行 → SUCCEEDED。

### 3.5 execute：幂等落库 + 退避 + 转人工

来源：[`m10_reliability.py`](../m10_reliability.py)

```python
def execute(self, task: dict, model_fn):
    tid = task["id"]
    try:
        result = model_fn(task["payload"], task["attempts"])
    except TransientError:
        attempts = task["attempts"] + 1
        if attempts >= MAX_ATTEMPTS:
            self._set(tid, "NEEDS_HUMAN", attempts=attempts)
        else:
            self._set(tid, "RETRY_WAIT", attempts=attempts, next_retry_at=time.time() + BACKOFF_BASE * 2 ** (attempts - 1))
        return "retry"
    except PermanentError:
        self._set(tid, "FAILED", attempts=task["attempts"] + 1)
        return "failed"

    # 幂等：唯一约束保证业务效果只写一次
    with self.conn:
        cur = self.conn.execute("INSERT OR IGNORE INTO effects(idem_key,result) VALUES(?,?)", (task["idem_key"], result))
        if cur.rowcount == 1:
            self.business_writes += 1  # 只有首次插入才算真实业务写入
    self._set(tid, "SUCCEEDED")
    return "success"
```

设计意图逐层拆解：

1. **错误分流**：TransientError 走退避/转人工，PermanentError 直接 FAILED。`model_fn(payload, attempts)` 把当前尝试次数传给执行函数，demo 的 flaky 函数据此「第 2 次成功」，精确演练「超时→重试→成功」。
2. **退避公式**：`BACKOFF_BASE * 2 ** (attempts - 1)`，attempts=1 等 0.05s、attempts=2 等 0.1s；attempts=3 达到 MAX_ATTEMPTS 转 NEEDS_HUMAN。
3. **幂等核心**：`INSERT OR IGNORE` + `rowcount == 1` 判定。重复执行时插入被唯一约束忽略，rowcount=0，`business_writes` 不增——「执行多次 = 写入一次」由数据库保证，不靠应用层「先查后写」（先查后写在并发下有竞态）。
4. **一个值得深思的窗口**：effects 落库与 `_set(tid, "SUCCEEDED")` 是**两个事务**。若中间宕机，任务仍是 RUNNING，租约过期后被回收重跑——`model_fn` 会再执行一次，但 effects 唯一约束保证业务效果不重复。这正是「租约回收必须配幂等」的原因：回收机制天然制造重复执行。生产中 `model_fn` 的副作用本身也要幂等——把 `idem_key` 传给下游业务 API（`create_activity_api` 的 `idempotency_key` 参数就是为此准备的），双层兜底。

### 3.6 cancel 与 drain

来源：[`m10_reliability.py`](../m10_reliability.py)

```python
def cancel(self, task_id: str) -> bool:
    row = self.conn.execute("SELECT status FROM tasks WHERE id=?", (task_id,)).fetchone()
    if row and row["status"] in ("PENDING", "QUEUED", "RETRY_WAIT"):
        self._set(task_id, "CANCELLED")
        return True
    return False
```

```python
def drain(eng: TaskEngine, worker: str, model_fn, max_steps: int = 40):
    """反复领取并执行，直到任务进入终态（自动处理退避等待）。"""
    for _ in range(max_steps):
        t = eng.claim(worker)
        if t is None:
            time.sleep(BACKOFF_BASE)
            continue
        eng.execute(t, model_fn)
        if eng.status(t["id"]) in ("SUCCEEDED", "FAILED", "NEEDS_HUMAN", "CANCELLED"):
            return
```

设计意图：cancel 的白名单就是「尚未产生业务效果」的状态集合；RUNNING 拒绝（返回 False 而非抛异常，调用方可提示「任务执行中，无法取消」）。被取消的 PENDING 任务即使 outbox 里还有未投递消息，dispatch 的 `WHERE status='PENDING'` 守卫也不会让它复活。drain 是演示/测试用的 Worker 循环：领不到任务就 sleep 一个退避基数再试（模拟等待 next_retry_at 到点），任务到终态即返回；`max_steps=40` 防止测试死循环。

## 四、工程要点与常见坑

1. **重复投递导致重复创建**
   现象：同一个教研活动被建了两条。原因：MQ at-least-once，消费端没有去重。对策：幂等键 + 唯一约束（`INSERT OR IGNORE`），selftest 断言 `business_writes == 1`；下游业务 API 再带一层 `idempotency_key`。永远不要假设消息只来一次。

2. **Worker 宕机任务永远 RUNNING**
   现象：用户确认后活动一直没建出来，任务卡 RUNNING。原因：没有租约，无人发现 Worker 已死。对策：lease_until + 心跳续租 + `reap_expired` 回收；`claim` 也可直接领取过期 RUNNING。演练方式就是 demo 第 2 幕：领取后不心跳。

3. **重试风暴打垮下游**
   现象：模型服务刚超时，海量立即重试让它彻底雪崩。原因：固定/零间隔重试。对策：指数退避写进 `next_retry_at`，claim 按时间闸门领取；生产再加随机抖动（jitter）避免重试同步化，并配合 m09 熔断。

4. **不可重试错误被无限重试**
   现象：参数非法的任务反复失败反复重试，日志刷屏。原因：所有异常一视同仁。对策：异常二分——`PermanentError` 直接 FAILED；`TransientError` 才有退避，且 MAX_ATTEMPTS 封顶转 NEEDS_HUMAN。

5. **取消 RUNNING 任务留下半完成状态**
   现象：取消「成功」了，但业务写入已经发生。原因：取消没有状态边界。对策：只允许 PENDING/QUEUED/RETRY_WAIT 取消；RUNNING 需要协作式取消（执行函数轮询取消标志，在副作用发生前退出），见练习 3。

6. **「库改了消息没发」**
   现象：任务状态是 PENDING 却永远没人执行。原因：改库与发 MQ 两步操作中间宕机。对策：Outbox 同事务；投递者只认 `published=0`，宕机重启续投，宁可重投（幂等兜底）不可丢投。

7. **租约短于任务耗时，健康 Worker 被误判死亡**
   现象：长任务执行到一半被另一个 Worker 领走，两个 Worker 并发执行。原因：LEASE_SECONDS 拍脑袋设太小且没心跳。对策：租约 > P99 执行时间或勤心跳（本模块 heartbeat 已备好）；即便双跑，幂等键仍是最后防线。演示值 0.2s 只为让演练秒级完成。

8. **把演示边界当生产能力**
   现象：直接拿 `:memory:` SQLite 上生产。原因：忽略示例边界。对策：README 第八节明确生产换 MySQL + RocketMQ + Redis；`check_same_thread=False` 是演示便利，多线程生产需连接池；§10 实战清单里的「数据库不可用」场景本模块未演练（覆盖的是超时/重复投递/宕机/取消），生产 POC 需补故障注入。

## 五、验收与测试

`selftest()` 五组断言与 §10 验收一一对应（来源：[`m10_reliability.py`](../m10_reliability.py)）：

```python
# 幂等
eng.enqueue("t1", "p", "k1"); eng.dispatch(); eng.redeliver("t1")
t = eng.claim("w"); eng.execute(t, lambda p, a: "ok")
t = eng.claim("w")
if t: eng.execute(t, lambda p, a: "ok")
assert eng.business_writes == 1 and eng.status("t1") == "SUCCEEDED"
```

```python
# 宕机回收
eng.enqueue("t2", "p", "k2"); eng.dispatch(); eng.claim("dead")
time.sleep(LEASE_SECONDS + 0.05)
assert eng.reap_expired() >= 1
t = eng.claim("w2"); eng.execute(t, lambda p, a: "ok")
assert eng.status("t2") == "SUCCEEDED"
```

```python
# 退避重试
eng.enqueue("t3", "p", "k3"); eng.dispatch()
n = {"c": 0}
def flaky(p, a):
    n["c"] += 1
    if n["c"] < 2: raise TransientError("x")
    return "ok"
drain(eng, "w3", flaky)
assert eng.status("t3") == "SUCCEEDED"

# 转人工
eng.enqueue("t4", "p", "k4"); eng.dispatch()
drain(eng, "w4", lambda p, a: (_ for _ in ()).throw(TransientError("x")))
assert eng.status("t4") == "NEEDS_HUMAN"

# 取消边界
eng.enqueue("t5", "p", "k5")
assert eng.cancel("t5") is True
eng.enqueue("t6", "p", "k6"); eng.dispatch(); eng.claim("w6")
assert eng.cancel("t6") is False
```

对照 §10 验收三句话：

- **「重复消息不产生重复业务操作」** → `business_writes == 1`（redeliver 制造重复投递后依然只写一次）。
- **「Worker 宕机后任务可恢复」** → `reap_expired() >= 1` 且换 Worker 后 SUCCEEDED。
- **「失败任务可追踪、重试或转人工」** → 超时重试后 SUCCEEDED（可重试）、持续失败 NEEDS_HUMAN（转人工）、状态全程可查（`status()`）。

一个诚实的细节：selftest 里重复投递后任务已 SUCCEEDED，第二次 `claim` 返回 None，并未真正触发第二次 execute——`INSERT OR IGNORE` 的兜底路径要靠「租约过期重跑」或手动重复 execute 才会走到（练习 2 专门验证它）。断言 `business_writes == 1` 守的是结果，两条路径都通向同一结果。

```bash
../../.venv/bin/python run_all.py           # 含 m10 的总验收
```

## 六、与其他模块的关系

- **[05 Agent 工作流编排](05-Agent工作流编排.md)（m05）**：m05 的 Checkpoint（SqliteSaver）解决「交互式流程中断后恢复」，m10 解决「后台异步任务的可靠执行」；生产中工作流的长任务节点应提交给 TaskEngine 这类引擎，而不是占着请求线程等模型。两者共同落实 §6「长任务状态必须持久化」。
- **[09 模型部署与路由](09-模型部署与路由.md)（m09）**：`model_fn` 内部调模型应经过路由器（合规/熔断）；m09 熔断防同步调用被拖死，m10 退避防异步重试风暴，两层节奏控制互补。`TransientError` 的典型来源就是模型超时（ProviderDown）。
- **[08 评测与质量门禁](08-评测与质量门禁.md)（m08）**：§12「重复业务写入 = 0」的门禁由本模块 `business_writes == 1` 断言守住；Golden Set 扩展类别「重复消息」可直接复用本模块演练。
- **[07 安全治理与人工确认](07-安全治理与人工确认.md)（m07）**：NEEDS_HUMAN 是 HITL 的入口之一；任务取消、转人工都应留审计记录（§10「失败任务可追踪」）。
- **[`common/business.py`](../common/business.py)**：`create_activity_api(ctx, draft, idempotency_key)` 是幂等的下游业务 API 模拟——任务层 effects 去重 + 业务层 `_IDEMPOTENCY` 去重，双层保险；最终写操作仍由原业务服务执行（§11）。

## 七、动手练习与延伸

1. **调参观察退避节奏**：把 `BACKOFF_BASE` 改成 0.5、`MAX_ATTEMPTS` 改成 5，在 execute 里打印 next_retry_at，观察间隔 0.5→1→2→4 的指数增长；再给间隔加 ±20% 随机抖动，思考为什么生产需要 jitter。
2. **直接验证幂等兜底路径**：对同一个 task dict 连续调用两次 `eng.execute(t, lambda p, a: "ok")`，断言 `business_writes` 仍为 1——亲眼看到 `INSERT OR IGNORE` 的 rowcount=0 分支。
3. **协作式取消 RUNNING**：给 tasks 表加 `cancel_requested` 字段，cancel 对 RUNNING 改为置标志而非拒绝，`model_fn` 在关键步骤前检查标志并提前退出（抛专用异常 → CANCELLED）。体会「取消边界」从状态约束扩展为协议约束。
4. **补一个补偿示例**：构造两步写任务（写 A 成功、写 B 抛 PermanentError），在 execute 的失败分支调用 A 的反向操作，使整体回到一致状态——把 §10 清单里本模块未覆盖的「补偿」补上。
5. **持久化 + 杀进程恢复**：`TaskEngine("out/tasks.db")` 落盘，enqueue/dispatch/claim 后直接杀掉进程，重启新进程 reap + claim 完成任务——把「Worker 宕机」从 sleep 模拟升级为真实进程级演练。
