# 09 · 模型部署与路由

> 对应源文档 §9 · 代码模块 [`m09_router.py`](../m09_router.py) · 运行：`../../.venv/bin/python m09_router.py`

## 一、这是什么 / 为什么重要

Teaching 的 AI 服务不会只有一个模型：意图识别这类高频轻任务适合便宜的私有小模型，复杂推理可能需要云端大模型，而涉及敏感数据的任务**只能**留在私有环境。于是产生三个工程问题：

1. **部署**：云端 API 怎么接（Key/协议/计费/限流）？私有模型怎么跑起来（vLLM/量化/显存）？
2. **路由**：一个请求来了，按什么规则选模型？任务类型、合规、成本、延迟、故障状态都要考虑。
3. **故障与合规的冲突**：私有模型挂了，能不能「聪明地」回退云端？——对 `PRIVATE_ONLY` 任务，**绝对不能**。这是 §9 用加粗语气写下的红线：「`PRIVATE_ONLY` 任务不能因为私有模型故障而自动回退到云端。」

源文档把本模块列为 P1（私有化和成本控制），但合规红线是 P0 级约束：一次「为了可用性」的自动回退，就可能把师生敏感数据送出私有边界，构成数据合规事故。可用性可以降级，合规不能降级。

[`m09_router.py`](../m09_router.py) 用模拟 provider 完整演示了 §9 的路由维度、熔断与合规回退策略。模块 docstring 明确了生产化路径：「生产把 `provider.invoke` 换成真实云 API / vLLM 调用即可（见 [`common/llm.py`](../common/llm.py) 的 openai 后端）」。本项目真实侧的私有部署由本地 Ollama 承担（qwen2.5:7b / qwen3:8b，见 [11 模型横向对比](11-模型横向对比.md)），路由决策所需的质量/延迟数据正是 m11 测出来的。

## 二、核心概念详解

### 2.1 云端模型接入

**定义与要点**（§9 云端模型清单）：API Key、Base URL、模型名、兼容协议、Token 计费、RPM/TPM（每分钟请求/Token 配额）、并发限制、超时、限流、重试、数据合规。

**为什么**：云 API 是「别人的服务」——配额会耗尽、网络会抖动、供应商会故障，客户端必须自带超时/重试/限流，而不是假设它永远可用。Key 是机密，§5 工程要求明确「Key 放在 Secret 或安全配置中心」。

**本项目体现**：[`common/llm.py`](../common/llm.py) 的 openai 后端就是云接入层——任何 OpenAI 兼容接口（OpenAI/DeepSeek/Qwen/vLLM/Ollama）统一走 `OpenAI(api_key, base_url, timeout, max_retries)`，超时默认 120s（`TEACHING_TIMEOUT`）、SDK 层重试默认 2 次（`TEACHING_MAX_RETRIES`），`LLM.stats` 累计 prompt/completion tokens 供成本统计。m09 的 `Provider.cost_per_1k`（元/1k token）与 `stats["cost"]` 则把「Token 计费」抽象成路由可用的成本维度。

### 2.2 私有化部署与推理

**定义与要点**（§9 私有化清单）：Hugging Face 模型权重、vLLM、GPU/CUDA、显存、FP16/BF16、AWQ/GPTQ/INT4 量化、KV Cache、Continuous Batching、Tensor Parallel。首期重点是**部署、调用、监控和评估**，不要求训练模型或优化推理内核。

逐个展开（理解层面即可）：

- **FP16/BF16**：半精度浮点。7B 模型 FP16 权重约 14GB 显存，再加 KV Cache 与激活，消费级显卡很快吃紧。
- **AWQ/GPTQ/INT4**：权重量化方法，把 16bit 权重压到 4bit，显存约降到 1/4，代价是少量精度损失——这是「私有小模型跑得起」的关键，也是小模型格式漂移更多的背景之一。
- **KV Cache**：缓存已生成 token 的注意力 Key/Value，避免重复计算；长上下文时它是显存大头。
- **Continuous Batching**：vLLM 的核心调度——请求随到随进批、完成即出批，而非等整批凑齐，大幅提升吞吐。
- **Tensor Parallel**：把一层权重切到多卡并行，单卡放不下的大模型靠它部署。

**本项目体现**：教学示例用 Ollama 在本地跑 qwen2.5:7b / qwen3:8b（OpenAI 兼容端点 `http://localhost:11434/v1`），等价于「私有化部署 + 兼容协议调用」的最小形态；m09 中 `Provider("private-qwen", "private", 0.0, 120, ...)` 的 `kind="private"`、零 Token 单价，正是私有模型「数据不出域、边际成本低」的抽象。生产换 vLLM 时只需替换 invoke 实现，路由逻辑不动。

### 2.3 模型路由的六个维度

§9 列出六个路由维度，与代码的对应关系如下（注意哪些已实现、哪些是统计/配置输入）：

| §9 维度 | 代码体现 |
|---|---|
| 任务类型 | `Provider.supports` 元组：`private-qwen` 支持 intent/extract/chat/embed，`cloud-gpt` 支持 intent/extract/chat/reason——embed 只有私有有，reason 只有云端有 |
| 数据合规 | `compliance` 参数：`PRIVATE_ONLY` 只保留 `kind="private"` 候选；`ALLOW_CLOUD` 才允许云端 |
| 成本预算 | `ALLOW_CLOUD` 排序键含 `cost_per_1k`；`stats["cost"]` 累计实际花费 |
| 质量要求 | 间接体现：`supports` 声明能力边界，真实质量数据由 m11 基准测出后反哺配置（7B 意图 87.5% vs 8B 100%） |
| 延迟 | `Provider.latency_ms` 记入 `stats["latency"]` 供观测；**当前排序键未含延迟**，延迟敏感分流靠 m11 数据人工配置（见坑 5） |
| 故障状态 | 熔断器：`fail_count` / `open_until`，打开的 provider 被 `_candidates` 剔除 |

**为什么按维度路由而不是「一个模型打天下」**：意图识别每天几万次、每次几百 token，用云端大模型既贵又慢还可能有合规问题；复杂推理私有小模型质量不够。路由让每个任务落到「质量够、成本最低、合规允许、当前可用」的模型上。

### 2.4 熔断（Circuit Breaker）

**定义**：某 provider 连续失败达到阈值后，暂时把它从候选池摘除（「打开」），冷却期内不再向它发请求；冷却结束后放一个试探请求，成功则恢复（「闭合」），失败则继续打开。

**为什么**：没有熔断时，每个请求都要先撞一次故障 provider、等满超时才回退——故障被放大成全局延迟飙升，重试风暴还会把半死的下游彻底打死。熔断用「快速失败 + 定期试探」保护双方。

**本项目体现**：`BREAKER_THRESHOLD = 3`（连续失败 3 次打开）、`BREAKER_COOLDOWN = 5.0`（冷却 5 秒）。成功调用会把 `fail_count` 清零（`_record_success`），所以阈值统计的是**连续**失败。冷却到期后 `_breaker_open` 返回 False，provider 重新成为候选——下一个请求就是试探：成功则计数清零恢复正常；失败则 `fail_count` 已 ≥3，`_record_failure` 立即把 `open_until` 再推后 5 秒。这是「单试探半开」的简化实现，没有显式的 HALF_OPEN 状态枚举，但行为等价。

### 2.5 合规红线：PRIVATE_ONLY 绝不回退云端

**定义**：任务被标记 `PRIVATE_ONLY`（数据不允许出私有边界）时，无论私有模型发生什么——故障、熔断、全部不可用——都只能失败，不能转投云端。

**为什么**：回退云端意味着把敏感 Prompt/数据发给外部供应商，违反数据合规。这类错误不可逆（数据发出去就收不回），所以宁可任务失败转人工，也不能「降级可用」。

**本项目体现**：代码里有**三道防线**（详见 3.4）：候选过滤只留私有；私有调用失败立即抛 `ComplianceError` 终止循环；候选为空时抛 `ComplianceError` 而非 `ProviderDown`。专用异常类型 `ComplianceError` 让上层能区分「合规拒绝」与「普通故障」——前者绝不应触发任何「换个模型再试」的兜底逻辑。

## 三、代码实现解析

### 3.1 异常类型：ComplianceError 与 ProviderDown

来源：[`m09_router.py`](../m09_router.py)

```python
class ComplianceError(Exception):
    """PRIVATE_ONLY 任务在私有模型不可用时抛出，绝不回退云端。"""

class ProviderDown(Exception):
    pass
```

设计意图：把「合规拒绝」建模为独立异常类型是关键决策。如果统一抛 `ProviderDown`，上层重试/兜底代码很容易「顺手」把它当普通故障处理而绕过合规。类型即语义：捕获 `ComplianceError` 的代码只能走失败/转人工路径。

### 3.2 Provider：模型配置的最小抽象

来源：[`m09_router.py`](../m09_router.py)

```python
@dataclass
class Provider:
    name: str
    kind: str               # cloud / private
    cost_per_1k: float      # 元 / 1k token
    latency_ms: float
    supports: tuple         # 支持的任务类型
    force_fail: bool = False
    fail_count: int = 0
    open_until: float = 0.0  # 熔断打开截止时间

    def invoke(self, task_type: str, tokens: int = 500) -> dict:
        if self.force_fail:
            raise ProviderDown(f"{self.name} 故障")
        return {"provider": self.name, "task": task_type, "tokens": tokens}
```

设计意图：一个 dataclass 同时承载**静态配置**（kind/cost/latency/supports，生产放配置中心）与**动态健康状态**（fail_count/open_until，运行时维护）。`invoke` 是唯一的模拟点：`force_fail` 开关用于演练故障，生产替换为真实 HTTP 调用（云 API 或 vLLM/Ollama 的 OpenAI 兼容接口）即可，路由/熔断/统计逻辑全部复用。`tokens` 默认 500 是估算值，用于成本累计；生产应传入真实 usage（`LLM.stats` 里有 prompt/completion tokens）。

### 3.3 _candidates：合规过滤 + 成本排序

来源：[`m09_router.py`](../m09_router.py)

```python
def _candidates(self, task_type: str, compliance: str) -> list[Provider]:
    pool = [p for p in self.providers.values() if task_type in p.supports and not self._breaker_open(p)]
    if compliance == "PRIVATE_ONLY":
        return [p for p in pool if p.kind == "private"]
    # ALLOW_CLOUD：私有优先（成本低），云端兜底
    return sorted(pool, key=lambda p: (p.kind != "private", p.cost_per_1k))
```

设计意图：三层筛选一次完成——**能力**（supports 含任务类型）、**健康**（熔断未打开）、**合规**（PRIVATE_ONLY 只留私有）。排序键 `(p.kind != "private", p.cost_per_1k)` 是个布尔技巧：私有得 False(0) 排前，云端得 True(1) 排后，同类内按单价升序。这实现了 §9 的成本维度：ALLOW_CLOUD 下私有优先（边际成本 0），云端兜底。注意合规过滤发生在排序**之前**——PRIVATE_ONLY 的候选池里根本不存在云端，排序再怎么排也排不出云端。

### 3.4 call：三道合规防线 + 顺序回退

来源：[`m09_router.py`](../m09_router.py)

```python
def call(self, task_type: str, compliance: str = "ALLOW_CLOUD", tokens: int = 500) -> dict:
    candidates = self._candidates(task_type, compliance)
    if not candidates:
        if compliance == "PRIVATE_ONLY":
            raise ComplianceError(f"PRIVATE_ONLY 任务 {task_type} 无可用私有模型，且禁止回退云端")
        raise ProviderDown(f"任务 {task_type} 无可用模型")

    last_err = None
    for p in candidates:
        try:
            result = p.invoke(task_type, tokens)
            self._record_success(p, tokens)
            return result
        except ProviderDown as exc:
            self._record_failure(p)
            last_err = exc
            # PRIVATE_ONLY：私有失败立即终止，不尝试云端
            if compliance == "PRIVATE_ONLY":
                raise ComplianceError(f"PRIVATE_ONLY 任务私有模型故障，禁止回退云端：{exc}")
    raise ProviderDown(f"所有候选模型失败：{last_err}")
```

三道防线逐一对照：

1. **候选为空**（私有全被熔断或不存在）：PRIVATE_ONLY 抛 `ComplianceError`，ALLOW_CLOUD 抛 `ProviderDown`——同为失败，语义不同。
2. **私有调用失败**：循环内 `if compliance == "PRIVATE_ONLY": raise ComplianceError` **立即终止**，绝不进入下一个候选。即使有人将来改坏了 `_candidates` 的过滤，这一道仍然兜底。
3. **候选过滤本身**（3.3）：正常情况下 PRIVATE_ONLY 的循环里压根没有云端 provider。

ALLOW_CLOUD 的行为则是标准的顺序回退：私有失败 → 记失败 → 试云端；全部失败才抛 `ProviderDown` 并携带最后一个错误。注意一个细节：私有失败但熔断未打开时，**下一个请求仍会先试私有**（排序不变），直到连续失败 3 次熔断打开才跳过——回退不是「拉黑」，熔断才是。这避免了单次抖动就永久改变路由偏好。

### 3.5 熔断与统计：_breaker_open / _record_success / _record_failure

来源：[`m09_router.py`](../m09_router.py)

```python
class ModelRouter:
    BREAKER_THRESHOLD = 3
    BREAKER_COOLDOWN = 5.0

    def _breaker_open(self, p: Provider) -> bool:
        return p.fail_count >= self.BREAKER_THRESHOLD and time.time() < p.open_until

    def _record_success(self, p: Provider, tokens: int) -> None:
        p.fail_count = 0
        s = self.stats[p.name]
        s["calls"] += 1
        s["cost"] += p.cost_per_1k * tokens / 1000
        s["latency"] += p.latency_ms

    def _record_failure(self, p: Provider) -> None:
        p.fail_count += 1
        self.stats[p.name]["failures"] += 1
        if p.fail_count >= self.BREAKER_THRESHOLD:
            p.open_until = time.time() + self.BREAKER_COOLDOWN
```

设计意图：
- `_breaker_open` 是**双条件**：计数达标且仍在冷却期。冷却到期后自动「半开」放行试探，无需后台线程去「关闭」熔断——时间本身就是状态机。
- `_record_success` 第一件事是 `fail_count = 0`：成功即清零，保证阈值语义是「连续失败」，偶发失败不会累积成误熔断。
- `stats` 按 provider 累计 calls/failures/cost/latency，对应 §9 验收「统计调用量、成本、延迟和失败率」。cost 按 `单价 × tokens/1000` 计；latency 累加的是配置标称值（演示用），生产应记真实墙钟耗时（见坑 6）。

### 3.6 default_router：两种模型配置

来源：[`m09_router.py`](../m09_router.py)

```python
def default_router() -> ModelRouter:
    return ModelRouter([
        Provider("private-qwen", "private", 0.0, 120, ("intent", "extract", "chat", "embed")),
        Provider("cloud-gpt", "cloud", 0.02, 80, ("intent", "extract", "chat", "reason")),
    ])
```

设计意图：满足 §9 验收「至少接入两种模型配置」。两个 provider 的能力集刻意**不完全重叠**：embed 只有私有（向量数据不出域），reason 只有云端（私有小模型推理不够）——于是「按任务类型路由」不需要额外规则，supports 过滤自然完成。demo 依次演示：intent→私有优先、reason→云端、PRIVATE_ONLY 故障拒绝回退、ALLOW_CLOUD 故障回退、连续 3 次失败熔断打开、最后打印各 provider 统计。

## 四、工程要点与常见坑

1. **PRIVATE_ONLY 故障时「好心」回退云端**
   现象：私有模型超时后任务却成功了，日志显示调用了云 API。原因：兜底逻辑只看「有没有可用模型」，不看合规标签。对策：本模块三道防线（候选过滤 + 失败即抛 `ComplianceError` + 空候选区分异常类型）；上层捕获 `ComplianceError` 只能失败/转人工，严禁再接重试。selftest 专门断言这条红线。

2. **没有熔断，故障 provider 拖垮全局延迟**
   现象：云端挂了之后每个请求都先等满超时才回退，P95 暴涨。原因：每次请求都「亲自」撞一次故障。对策：连续失败 3 次打开熔断，冷却期内直接跳过；冷却后单试探恢复。5s 冷却与 3 次阈值是演示值，生产需按供应商 SLA 与流量校准。

3. **成功不清零失败计数**
   现象：provider 早已恢复，却仍被间歇性熔断。原因：历史失败累积，阈值变成「累计失败」而非「连续失败」。对策：`_record_success` 首行 `p.fail_count = 0`。

4. **把合规拒绝当普通故障重试**
   现象：`ComplianceError` 被通用 retry 装饰器捕获后又发起调用。原因：异常类型混用。对策：合规拒绝用独立异常类型，重试策略显式排除它；错误码映射到前端时也不泄漏内部细节（§5 工程要求）。

5. **以为延迟参与了路由排序**
   现象：延迟敏感任务仍被路由到慢模型。原因：当前 `_candidates` 排序键只有「私有优先 + 成本」，`latency_ms` 仅进统计。对策：认清现状——延迟分流靠 m11 实测数据反哺配置（7B 1.62s vs 8B 13.67s，意图抽取选 7B）；练习 1 把延迟加入排序键。

6. **成本/延迟统计用估算值冒充实测**
   现象：成本看板与账单对不上。原因：`tokens=500` 是默认估算，`latency_ms` 是配置标称值。对策：生产 invoke 返回真实 usage 与墙钟耗时再记账（`LLM.stats` 已有 token 计数可接）；估算值只用于演示。

7. **Key 与配置硬编码**
   现象：API Key 出现在代码仓库里。原因：图省事写死。对策：§5 要求 Key 放 Secret/配置中心；本项目用环境变量（`OPENAI_API_KEY` 等），Provider 静态配置生产应放 Nacos 并支持热更新，健康状态留在运行时内存。

## 五、验收与测试

`selftest()` 断言（来源：[`m09_router.py`](../m09_router.py)）：

```python
def selftest() -> None:
    r = default_router()
    assert r.call("intent")["provider"] == "private-qwen"
    assert r.call("reason")["provider"] == "cloud-gpt"

    r.providers["private-qwen"].force_fail = True
    try:
        r.call("intent", compliance="PRIVATE_ONLY")
        raise AssertionError("PRIVATE_ONLY 不应回退")
    except ComplianceError:
        pass
    assert r.call("intent", compliance="ALLOW_CLOUD")["provider"] == "cloud-gpt"

    r2 = default_router()
    r2.providers["cloud-gpt"].force_fail = True
    for _ in range(3):
        try:
            r2.call("reason")
        except ProviderDown:
            pass
    assert r2._breaker_open(r2.providers["cloud-gpt"])
```

逐条对应 §9 验收标准：

- **「至少接入两种模型配置」**：`default_router` 的 private-qwen + cloud-gpt（真实侧另有 common/llm 的 mock/openai 与 m11 的三模型）。
- **「能按任务路由」**：intent→私有（成本优先）、reason→云端（能力过滤），两条断言分别验证成本维度与任务类型维度。
- **「故障回退不能绕过合规策略」**：私有 `force_fail` 后，PRIVATE_ONLY 必须抛 `ComplianceError`——注意 `raise AssertionError("PRIVATE_ONLY 不应回退")` 这个陷阱断言：如果 call 竟然成功返回，测试立即失败；同一故障下 ALLOW_CLOUD 则必须回退到 cloud-gpt。一拒一放，红线与可用性同时验证。
- **熔断**：cloud-gpt 连续失败 3 次后 `_breaker_open` 为 True。
- **「统计调用量、成本、延迟和失败率」**：`stats` 结构承载，demo 末尾打印（selftest 未对数值断言，属观测能力）。

```bash
../../.venv/bin/python run_all.py      # 含 m09 的总验收
```

## 六、与其他模块的关系

- **[03 模型接入与流式接口](03-模型接入与流式接口.md) / [`common/llm.py`](../common/llm.py)**：m09 的 `Provider.invoke` 生产化就是换成 llm.py 的 openai 后端调用；超时/重试/Token 统计在那一层，路由/熔断/合规在这一层，职责分离。
- **[11 模型横向对比](11-模型横向对比.md)（m11）**：路由的「质量/延迟」维度需要数据说话——m11 测出 7B 87.5%/1.62s、8B 100%/13.67s，README 据此给出「延迟敏感意图用 7B + 归一化兜底，质量敏感用 8B」的分流建议，这正是 m09 按任务路由的配置依据。
- **[08 评测与质量门禁](08-评测与质量门禁.md)（m08）**：路由配置变更后必须重跑门禁，确认换模型没有把质量换没了。
- **[10 分布式可靠性](10-分布式可靠性.md)（m10）**：互补关系——m09 熔断保护「同步调用」不被故障 provider 拖死；m10 的 `TransientError` 退避重试处理「异步任务」的模型超时。异步任务调用模型时同样应经过路由器的合规约束。
- **[07 安全治理与人工确认](07-安全治理与人工确认.md)**：PRIVATE_ONLY 是数据合规在模型层的投影，与多租户/脱敏同属 §11 安全治理体系；合规失败转人工（NEEDS_HUMAN）衔接 HITL。

## 七、动手练习与延伸

1. **把延迟加入排序键**：修改 `_candidates` 的 ALLOW_CLOUD 排序为 `(kind != "private", latency_ms, cost_per_1k)` 或加权打分，用 demo 观察路由变化；思考为什么不能只看延迟不看合规（合规永远是硬过滤，不进打分）。
2. **接真实私有 provider**：把 `Provider.invoke` 换成 `LLM("openai", model="qwen2.5:7b", base_url="http://localhost:11434/v1", api_key="ollama").chat(...)`，记录真实耗时进 stats，跑一遍 PRIVATE_ONLY 故障演练（停掉 Ollama 即可制造故障）。
3. **加第三个 provider 与 RPM 限流**：增加一个云端备用模型，给 Provider 加 `rpm_limit` 字段，在 `_candidates` 里过滤超配额的 provider——体会 §9「RPM/TPM、并发限制」如何进入路由。
4. **显式半开状态**：把熔断重构为 CLOSED/OPEN/HALF_OPEN 三态，冷却后只允许一个试探请求（并发下用锁或原子标志），对比重构前后行为是否等价。
5. **统计看板**：把 `stats` 导出为 JSON，计算失败率与平均延迟，对照 §9 验收「统计调用量、成本、延迟和失败率」补一个最小看板；生产接 Micrometer/OpenTelemetry（README 第八节）。
